# BNB Guardian V0.0.3 五次真实功能操作方案

此计划是条件式执行方案，不是虚构交易或自动发交易安排。没有真实需求就不执行，不保证三天内凑齐五次。

## 前置条件

官方报名证据可核实；Guardian 身份属于报名钱包；正式服务与 AI 持续可用；HelloFugu 上架成功；用户已确认本次任务、支出上限和交易草稿；客户确有 Venus 测试网风险管理需求。当前报名钱包没有测试币及待偿还债务，需要实际客户/真实测试需求，不能为计数故意制造危险仓位。

## 条件式三日窗口

| 窗口 | 预期工作数 | 可执行条件 |
|---|---:|---|
| Day A，首个通过前置检查的 UTC 日期 | 2 | 两个真实且不同的风险管理任务 |
| Day B，A 后至少 24 小时、另一 UTC 日期 | 2 | 新出现的两项合法风险任务 |
| Day C，B 后至少 24 小时、第三 UTC 日期 | 1 | 新出现的合法风险任务 |

原借贷风险已解决后不重复交易。不能将同一个偿债故意拆成五笔，不为达标修改触发阈值，也不能借回资产形成循环。日界线采用 UTC 工程解释，官方最终解释待确认。截止前没有五项需求就如实保持 qualified=false。

## 每项任务的执行和验收

1. 读取真实 Venus 区块快照，核对 Comptroller、oracle、抵押因子、VAI 不支持状态、借款余额。coverage < 1.25 才触发，目标 1.50。客户需求和授权记录存本地；不要将非公开客户信息公开上链/GitHub。
2. 固定允许的 vBNB/vUSDT/vUSDC，确定性 bigint 计算金额和支出 cap；AI 只解释，不决定金额。拒绝主网、未知市场、零额度、无债务及健康仓位。
3. `prepare repay` 生成短有效期草稿、planHash、模拟及 Gas；需要 ERC20 allowance 时只精确授权，单独确认。授权不计功能交易。
4. 用户在钱包核对网络、目标、金额、余额、期限，手动签名发送。未确认不发送。过期后重新读取风险、仿真和出草稿，不直接重发旧计划。
5. 记录客户端计划哈希、实际 transaction hash、borrower、市场、前后快照、用户批准记录和回执。`RepayBorrow` > 0，receipt.status=1，无 Venus Failure，前区块风险触发且后区块债务减少，才进入功能审计。规则不能证明 intra-block 顺序或代理钱包时标记人工复核，不推定通过。
6. `npm run qualify` 重查链上证据；去重 hash、按区块时间生成 UTC 日期。注册、上架、查询、授权、订阅、结算全部排除功能计数。

## 雇佣与公平性

我们的报名钱包真实雇佣三个不同 Agent，跨两个指定市场；外部三名客户用他们独立持有、非我们控制或资助的钱包支付并完成真实服务。不得提供“代付 Gas”或资助独立客户以绕过外部雇佣门槛。普通水龙头领测试币和共同来源是否影响最终独立性，由主办方判断，报告不会单凭回执声称钱包独立。

保存订阅和结算交易、签名绑定的服务交付哈希、完成状态。不能伪造用户、假订阅、到期前撤销完成任务，也不能把平台团队的历史订阅当我们的客户。
